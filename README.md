# rt511

rt511 brings roadside traffic-camera feeds into a ranked wall, combines road-aware scoring with JEV-assisted reasoning, and shows how activity at one camera draws attention along the road network. It explores a simple question: when there are more traffic cameras than anyone can watch at once, where should attention go?

The idea draws on **Information Foraging Theory**, which studies how people search for clues in crowded environments. Instead of making an operator click through thousands of quiet highway feeds, rt511 lays down a trail of "scent." When a camera picks up something unusual, the system raises its ranks and pulls attention upstream and downstream along the road, following where delays and shockwaves actually travel.

Attention starts with a scoring equation: a camera ranks higher when its feed is unusually busy or slow for that hour, when the corridor carries heavy traffic, and when reported incidents back it up. A vision-reasoning model then takes a second look at the top-ranked feeds to verify what is actually happening.

The complete math, graph models, and software design are detailed in the [whitepaper](docs/rt511_visual_attention_whitepaper.md). rt511 uses public feeds from agencies whose written terms permit third-party display. It currently covers California, Iowa, Ohio, Oregon, Maine, New Hampshire, and Vermont - 7,394 cameras in all.

It is a demonstration based on my idea that how we can comfort the information foraging theory applied to the traffic camera. It is originally proposed as a theory to understand how human users search for information. The [whitepaper](docs/rt511_visual_attention_whitepaper.md) describes the theory and concept behind and actual software design.

The front page shows the covered states floating in a row, with each camera lit by the sun's position over it. Pick a city, and its cameras are mapped across the road network and ranked live on the wall. A red LIVE badge marks streaming video, while a SNAPSHOT tag counts down to the camera's next still image.

## Getting Started

### Prerequisites
* Node.js 22+ with pnpm
* Python 3.12+ with uv

### Quickstart

```
make setup     # installs dependencies and builds road graphs for 29 cities (~30m)
make start     # builds and serves the wall at http://127.0.0.1:8511
```

Note on setup: `make setup` queries OpenStreetMap at rate-limited intervals to build network topologies. If interrupted, re-run the command and completed cities are cached.

All 29 default cities work out of the box without authentication. Images and streams are public.

### Configurations & Keys

```
uv sync
pnpm install
cp .env.example .env
```

| Key | Source | Purpose |
| OHIODOT_API | [OHGO Portal](https://publicapi.ohgo.com/docs/registration) | Refreshes Ohio camera lists and incident feeds. |
| OREGONDOT_API | [TripCheck Portal](https://apiportal.odot.state.or.us/) | Refreshes Oregon camera lists. |
| JEV_API | Provider token | Enables the typed reasoning model, which reads numbers and text, for incident and still-picture arbitration and the second-look reranker. |
| RT511_DETECTOR_URL | Custom endpoint | Points to the vehicle detector (defaults to [http://127.0.0.1:8513](http://127.0.0.1:8513)). |


Without agency keys, Ohio and Oregon cameras use bundled metadata snapshots. `JEV_API` is optional. It turns on the second look described below. Without it, ranking runs entirely on the analytical scoring equation.

### Running the wall

```
pnpm start
```
Open [http://127.0.0.1:8511](http://127.0.0.1:8511). Press Ctrl+C to terminate.

**On-Demand Polling**: Cameras are not polled until you open a city. When you navigate away, polling terminates after two minutes. An idle server generates zero network requests.

#### CLI Options
Pass flags through `pnpm start` or the underlying binary:
```
pnpm start --regions oakland-ca,des-moines-ia   # Polls specific cities continuously (kiosk mode)
pnpm start --cameras freeway                    # Restrict ingestion to freeway corridors
pnpm start --port 8512                          # Bind on an alternate port
pnpm start --ring 30                            # Extend in-memory replay buffer (minutes)
```

### Capabilities & Visual Modes
#### Attention Modes

* **Which Would You Watch?** (`Which?`): A browser-based pairwise comparison tool. Choose between two unlabelled camera frames, or skip. In Learn Mode, the system reveals its scoring breakdown after each pick and fits an in-browser Bradley–Terry model to your visual choices (evaluating motion, road class, incident flags, and lighting). After 10 choices, you can toggle the wall to rank feeds by your learned visual preference. Stored locally; exportable to JSON.

* **Evaluate** Compares your preferences against the scoring engine and JEV models using double-blind pairs. Run `uv run python scripts/evaluate_attention.py <export>.json --logs out` to evaluate rank correlations.

* **The Second Look** When `JEV_API` is configured, an asynchronous typed reasoning model compares the top eight candidate feeds, from their numbers and text, every few minutes, scaling the dynamic movement term ($0.75\times$ to $1.25\times$) while preserving baseline incident floors. Logs stream to `out/jev-<date>.jsonl`.


#### Dynamic Map Overlays
* **Attention Spreading** Renders real-time spatial scent diffusion on the city map. When a camera detects an incident or abrupt deceleration, upstream feeds gain elevated scoring baselines to anticipate queue growth. The interface projects directed trails along roadway links: white for kinetic anomalies, orange for stopped queues, red for reported incidents.

* **City Pulse**: A timeline sparkline beneath each city in the national list, rendering minute-by-minute median frame differences normalized to each city's peak rush-hour amplitude.

* **Snow Detection**: A heuristic detector that monitors daytime pixel desaturation across camera fields. When three or more cameras in a metro turn uniform white under daylight conditions, the city is flagged for winter road conditions on the national map.

* **Night Shift**: Once local sunset passes at a camera's coordinates, frame overlays display active vehicle counts derived from the zero-motion inference engine (e.g., 3:12 AM · 2 cars).

#### Exploration Tools
* **Road Trip**: Traverses highway corridors sequentially (e.g., `I-235 Eastbound`), lingering on live streams or segments with high spatial separation before stepping to the next downstream node. Deep-linkable via URL hash (`#trip=I-235:eastbound`).

* **Sun Relay**: Tracks the evening terminator westward across the continent, handing off from Atlantic cities (Portland, ME) to Pacific corridors (Portland, OR; Los Angeles), tracking golden hour and night transitions. Deep-linkable via `#relay`.


### The Vehicle Detector (Optional)

The vehicle detector runs alongside the server as an independent service on port `8513`. It counts the vehicles in a frame that the zero-motion gate has flagged and hands the count to the reasoning model as evidence. It needs the YOLO26 weights in `data/models/`, which are not part of this repository (see [License](#license)).

```
make detect        # CUDA/Metal hardware-accelerated inference
make detect-cpu    # CPU fallback
```

Requires YOLO weights placed in `data/models/`. Dependencies can be installed manually via `uv sync --extra detector`.

### Adding a city

New metropolitan regions are constructed through the CLI pipeline:

```
# 1. Discover endpoints and dense camera clusters
uv run rt511 sources
uv run rt511 metros --top 20 --name

# 2. Define, ingest, and bind to OpenStreetMap topology
uv run rt511 city "Des Moines, IA" --radius 12 --limit 60
uv run rt511 catalog --region des-moines-ia
uv run rt511 build --region des-moines-ia

# 3. Attach empirical baseline counts (where agencies publish AADT/sensor data)
uv run rt511 counts --region des-moines-ia
```

Or run he bundled shortcut:
```
make add-city CITY="Ames, IA"
```

`sources` lists the agencies this project reads, what each one publishes, and its terms. `metros` shows where cameras cluster, so you can pick somewhere worth watching. `city` geocodes the name, works out which source covers that state, keeps the cameras nearest the center, and saves the region. `catalog` reads the cameras' details from the agency's feed, and `build` matches them to roads. `counts` joins the agency's published traffic counts, where it publishes them under terms that allow it, so the scorer knows how big each road is from a measurement rather than from its road class. A city in a state with no source is refused.


## System Architecture & Technical Specifications

For full system diagrams and data flow specifications, see [`docs/architecture.md`](docs/architecture.md).

### Component Breakdown

| Directory | Language / Stack | Role |
|---|---|---|
| `src/rt511/` | Python (`shapely`, `networkx`) | Offline pipeline. Geocodes cameras, runs road-matching heuristics, and builds spatial corridor graphs. Run on demand. |
| `server/` | TypeScript (Node.js) | Core daemon. Serves the API, hosts the in-memory circular snapshot buffer, and delivers compiled client assets. |
| `web/` | React, TypeScript | Canvas/WebGL wall interface, map renderer, and in-browser Bradley–Terry preference engine. |
| `shared/` | TypeScript | Shared schemas, protocol definitions, and telemetry data models. |


### Data Privacy & Zero-Retention Architecture

`rt511` is designed as an ephemeral viewing lens, not a surveillance archive:

* **Direct-to-Client Video**: Video streams never transit or terminate on the backend server. The browser negotiates playback directly with the agency's origin CDN via public HLS endpoints only while a camera modal is active. Closing the modal terminates the session and purges client memory buffers.
* **Volatile In-Memory Frame Ring**: The server maintains a short ring buffer in volatile RAM solely to allow scrubbing recent frames. **No images or video chunks are written to disk.** Restarting the daemon purges all stored frames.
* **Localhost Scoping**: The API daemon binds exclusively to loopback (`127.0.0.1`).
* **Text-Only Storage**: Persistent disk artifacts are strictly non-media text files: normalized OpenStreetMap road topologies, camera registry metadata, and newline-delimited JSON telemetry logs in `out/`.


### Ingestion Budgets & Upstream Rate Limiting

To minimize load on state DOT infrastructure, `rt511` enforces strict global rate limiting designed to match or undercut a single human visitor browsing a state 511 portal:

* **Global Ingestion Quota**: Capped at **1 request / 5s** for on-screen cameras and **1 request / 10s** for off-screen cameras per agency, regardless of wall dimensions.
* **Conditional Headers**: All polling leverages HTTP `ETag` and `If-Modified-Since`. Unchanged frames return `304 Not Modified` payloads (~300 bytes).
* **Zero Idle Polling**: Cities with no active browser sessions remain dormant; the server issues zero network requests until a client connects.
* **Explicit User-Agent**: Every request carries an identifying header referencing the project repository. Borrowed `Referer` headers and session tokens are strictly avoided.

#### Ingestion Latency Characteristics

Because polling is strictly rate-limited, wall behavior reflects these operational constraints:

1. **Initial Wall Warmup**: A 40-camera city takes approximately 3 minutes to populate all tiles (1 frame per 5s per agency). Scores appear once a tile acquires its second comparative frame.
2. **Refresh Cycles**: On-screen tiles refresh every 1 to 3 minutes depending on agency camera density.
3. **Focused Camera Acceleration**: Opening a specific camera modal triggers dedicated polling matched to that agency's native publish rate (e.g., every 5s in Ohio).

### Spatial Topology & Corridor Graph Matching

`rt511` converts flat camera lists into traversable directed highway corridors by projecting camera locations onto OpenStreetMap road networks.

```
[ Upstream Camera ] (Site A)
           │
           ▼  <free-flow travel time, length, road class>
   =================== Freeway Mainline ===================
           ▲
           │
[ Downstream Camera ] (Site B)
```

* **Site Clustering**: Sensors within 40 m on the same carriageway collapse into a single topological site. Mainline freeways and surface/frontage links never share a site.
* **Scored Route Alignment**: Cameras bind to corridors via scored route matching rather than naive nearest-neighbor projection. Route numbers extracted from metadata separate freeways from parallel frontage roads. Intersection cameras are explicitly isolated from express carriageways.
* **Bidirectional Handling**: When an agency omits travel direction codes (e.g., Iowa DOT), the site is modeled as spanning both carriageways rather than arbitrarily snapping to a single side.
* **Directed Edges**: Directed edge $(A, B)$ forms if the shortest path along the network contains no intermediate camera site, does not pass within 60 m of an unrelated sensor, and has a circuitousness ratio $\le 2.5\times$ Euclidean distance.
* **Edge Classes**: Segments are classified as `freeway`, `ramp`, `street`, or `nearby` (virtual links bridging parallel one-way pairs or divided carriageways).
* **Validation Checks**: Graph builds validate direction codes against carriageway geometry, verify milepost monotonicity, and flag near-reversals ($>90^\circ$ disagreement with signed highway direction).

### Hardware Footprint & Resource Utilization

* **Memory Footprint**: Base topology requires ~40 MB RAM per active city. Frame ring buffers scale with `camera_count × ring_depth × frame_size` (typical frames: 20–200 KB). Configure depth with `--ring <minutes>` (default: 10 frames).
* **Render Overhead**: The 2D map engine runs entirely via client WebGL/HTML5 canvas, executing at ~34 ms/frame during pan and zoom interactions on modern desktop hardware without dedicated GPU acceleration. Zero render cycles are consumed while static.

## Theory at a Glance

This section outlines the baseline assumptions governing how attention is scored and allocated. It represents one explicit hypothesis designed to be measured, tested, and compared against alternative ranking models. The complete mathematical formulation, empirical constants, and academic references are detailed in the [whitepaper](docs/rt511_visual_attention_whitepaper.md), with operational notes in [`docs/attention.md`](docs/attention.md).

* **Temporal Anomaly**: Incoming frames are downsampled to grayscale thumbnails and differenced against preceding captures. The resulting delta is normalized against a rolling baseline learned for that specific hour of the week. Expected baseline activity scores at $0.5$, while variance exceeding twice the historical norm saturates the term. Cameras lacking sufficient observation history are clamped to prevent artificial volatility.
* **Corridor Importance**: Roadway priority scales the baseline motion term by a multiplier between $0.5\times$ and $1.5\times$. Ground truth is derived hierarchically: measured agency AADT counts when published, lane count and design speed limits when available, and standard functional road classification as a fallback.
* **Consequence Before Movement**: Confirmed incidents, upstream queue propagation, and verified stationary traffic apply numerical *floors* to a camera's score rather than additive bonuses. The score is built in two bands, so any camera held by a floor of at least $0.2$ ranks above every camera without one, and floor-held cameras take at most half of the wall's prominent tiles. Because zero-motion frames (gridlock vs. an empty overnight road) appear identical under simple pixel differencing, this ordering keeps severe bottlenecks on the wall.
* **Directed Network Topology**: Sensors are mapped to directed roadway corridors matching real-world traffic flow. Queue risks diffuse exclusively upstream, bounded by kinematic wave speeds and elapsed incident duration. An incident, confirmed stopped traffic, or movement well above a camera's usual level prompts closer polling of its neighbors within two hops, upstream first.
* **Selective Semantic Reasoning**: The JEV typed reasoning model, which reads numbers and text rather than images, acts strictly as an exception handler for ambiguities that numerical heuristics cannot resolve. It arbitrates zero-motion ambiguities (gridlock vs. deserted road, while a frozen feed is detected by the server itself), selects optimal camera perspectives during active incidents, and re-ranks top candidate feeds during periodic second-look sweeps. Model outputs are strictly bounded, confidence-gated, and barred from overriding topological incident floors.
* **Human Visual Alignment**: The *Which?* inspection tool fits an in-browser Bradley–Terry preference model to pairwise user choices across identical feature vectors. This projects operator instinct directly into the scorer's feature space, enabling quantitative evaluation between algorithmic rank, the reasoning model's second look, and human choice.
* **Display Allocation & Hysteresis**: Feeds are allocated screen area proportionally by ranked score. A hysteresis buffer prevents rapid tile-swapping and visual flicker when adjacent feeds hover near rank boundaries.

### Agency-Specific Handling
* **Oregon (ODOT)**: ODOT terms mandate displaying its statutory liability disclaimer wherever imagery appears. The modal viewer renders this notice in full for all Oregon feeds.
* **Ohio (ODOT)**: Enforces per-key ingestion caps. The engine's global poll scheduler operates well below published rate limits.

* **Unlisted Jurisdictions**: Agencies that prohibit third-party consumption, limit usage to personal browsing, or require private negotiated contracts are excluded by design.
